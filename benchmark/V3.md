## 本版修改

|项目|v3 规则|
|---|---|
|总规模|7 场景 × 4 任务 × 2 人物规模 × 2 最终视角，112 个基础配置|
|镜头数|每配置选一个长度；三镜头 56 条、四镜头 56 条，每任务各 14 条，不扩为 224 条|
|素材|每场景的两段素材都用于每种任务，各覆盖 2 条；每段素材仍对应 8 条|
|事件位置|三人布局轮换相邻两座上的 A/B；四人布局还轮换 focal pair 所在的一侧|
|离屏条件|所有 partial 都保留至少一名未变化、最终未提及的画外人物；四镜头新增一次 partial，不新增事件|
|空间描述|厨房用 window/aisle 替代无物理定位的 guest/cook；客厅说明沙发与扶手椅的相对布局|
|全景覆盖|反打保留反向地标，俯拍明确包含方向地标；稍偏离桌端中心，避免将同侧前后座强制投影重叠|
|身份|继续使用既有均衡的性别 + 衣服颜色，保持反打/俯拍配置的人物锚点相同|
|评分|仍只在最终全景两帧上计算 Valid、Count、Position、SR；partial 仅作观察历史与独立诊断|

布局中的 visible_seats 仍是预期覆盖，不是三维几何可见性证明。地标是否足够清楚、全景是否可拍，仍须人工和视频验证。三人版不让端座承担移动事件，以保留明确的相邻双人局部镜头；不能宣称已覆盖所有可能换位。

素材和长度通过确定性分配表独立于生成结果选择。反打/俯拍的同配置保持来源、人物、事件位置和长度相同，但两份自然语言 Content 仍由独立构造请求生成，不能据此宣称纯视角因果对照。14 段素材及共享布局带来的关联要保留在统计中；该设计不是所有变量完全交叉的随机实验。

## 构造与校验

在 benchmark 目录执行。默认命令不访问网络、不读取 API 密钥：

    python3 generate_core_v3.py

正常的每条构造仍为五次独立 OpenRouter 调用：原文抽象 → 人物属性 → 故事规划 → Content 渲染 → 独立审校。相机、状态和隐藏答案由 Python 确定。失败尝试保留；不将离线测试的模拟返回写入正式目录。

下列命令会产生提示词构造的 LLM 费用，只有显式执行才运行；不生成视频：

    python3 generate_core_v3.py --execute --limit 4
    python3 generate_core_v3.py --execute

每个样本沿用 prompt.txt、prompt.public.json、episode.internal.json、annotations.hidden.json、run.json 和阶段日志。已经完成的样本不会重生成；损坏或与计划不符的已完成产物标为 needs_repair，不静默覆盖。只规划时不产生可冒充真实输出的占位 prompt。

    python3 generate_core_v3.py --validate
    python3 -m unittest discover -s tests -q

严格验证在任何样本 pending 时返回失败。设计检查通过与全量生成验证通过是两个不同状态。版本输出目录禁止设为 v2 或其父目录。

未来选择全量评测可使用 run_evaluation.py 的 --all-cases，并显式指定 v3 dataset 和新的 evaluation 输出目录；当前样本未生成，该入口会拒绝提交。每镜 3 秒仅决定 9/12 秒总预算，公开 prompt 不含时长。

## 两帧人工校准

已从旧十条视频重新提取最终全景内 0.25、0.75 两个时点，不是从旧五帧中删掉三帧。身份参照仍为每个身份建立镜头三帧。使用源批次全部十条，不按旧评分选取。

打开本地标注入口（本地历史产物，未随仓库上传；`calibration/pilot-10-two-frame/blind/index.html`）。逐项完成后，页面导出 item-XXX.human.json，将其放入 calibration/pilot-10-two-frame/human。页面不包含任务、期望人数、目标座位分配或原裁判答案。private 目录仅用于后续确定性对照，标注者不要读取。

以下 prepare 操作仅本地抽帧；已有包拒绝覆盖，新包需另指定输出目录：

    python3 calibrate_judge.py --phase prepare

人工标注应先独立完成。下面的 judge 命令才会向 OpenRouter 上传该包的图片并产生费用；同一 Sol 单裁判、相同两帧协议，不做逐例仲裁，也不向裁判传入人工答案：

    python3 calibrate_judge.py --phase judge --execute
    python3 calibrate_judge.py --phase compare

compare 不访问网络，报告原始人数/完整座位读数一致性、四个分数的一致性及 Valid 混淆表。Count/Position 分数一致性以人工判定有效的 case 为分母，裁判误拒绝算不一致；未填人工项或未执行裁判不会被记成通过。两种不同的错误人数即使得到相同 Count 分，也会在原始读数一致性中暴露。

这十条是已经用于调试的开发校准材料，不是独立 held-out 可靠性证据，也不是 v3 新样本结果。当前人工与裁判标注均未执行，无一致率。正式发布前还需在未用于修规则的独立材料上确认可靠性；不能把开发校准的一致率当作无偏准确率。
